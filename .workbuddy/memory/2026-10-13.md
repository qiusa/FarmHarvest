## 修复：蔬菜增删改后主界面不同步
### 根因
`CropStore.presets` 是**计算属性**（每次调用都重读文件），但 SwiftUI 视图里直接 `ForEach(CropStore.presets)` 不构成 @State 依赖 —— 弹窗里改了JSON 文件，SwiftUI 不知道数据变了，body 不会重绘，主界面蔬菜列表保持旧值。
另一个问题：`.sheet(isPresented:)` 的 `onAdded` 闭包**只在新增时回调**，删除和修改都不通知。

### 修复（ContentView.swift）
- 新增 `@State private var presets: [CropPreset] = CropStore.presets`，`ForEach` 改用这个缓存。
- 新增 `reloadPresets()`：重读 presets；**若当前 selectedPresetID 已不存在则自动切到第一个**（含时长/收菜时间回填）；若仍存在但时长被改，同步刷新 hoursText/minutesText。
- `.sheet(isPresented:onDismiss:)` 加 `onDismiss: { reloadPresets() }` —— 这是关键，无论新增/删除/修改都在关闭时统一刷新。
- `onAdded` 里也调 `reloadPresets()`，并补上原先漏掉的 `harvestDate` 回填。
- `onAppear` 用 reloadPresets() 代替直接读 CropStore.presets。

### 验证
用 swiftc 复刻 reloadPresets 逻辑跑了 5 个场景，全部正确：删非选中项（保持选中+同步时长）、删选中项（自动切换到第一个）、改选中项时长（时长框同步）、删到空（清空选中）、内置 hidden 机制。

### 通用教训
**SwiftUI 里凡是「外部可变更的数据源」，必须缓存成 @State 并提供显式刷新入口。** 直接在 body 里读计算属性/单例不会建立依赖关系，数据变了 UI 不会更新。配 sheet 的 onDismiss 是最可靠的刷新时机。

## Widget 同步根因定位与解决：改用 Developer ID 签名

### 关键实验（决定性证据）
写了一个最小 .app bundle（Info.plist + 可执行文件 + App Group entitlements），分别用两种签名跑同一个探针：
- **adhoc（`codesign --sign -`）**：exit=3，`WRITE_FAIL You don't have permission to save the file ... NSCocoaErrorDomain Code=513`
- **Developer ID（`Developer ID Application: ZheJiang Yixin Technology Co., Ltd. (MWYKGVPTJP)`）**：**exit=0，WRITE_READ_OK**

**结论：macOS App Group 权限校验的是签名里的真实 TeamID。adhoc 签名没有 TeamID，系统虽返回容器路径（containerURL 非 nil），但不给写权限 —— 这就是「Widget 不同步」的根因，也解释了之前为何 containerURL 非 nil 却写不进去。**

### 关键认知修正
之前 CropStore 注释里写的「macOS 上必须用 TeamID 前缀的 App Group，无需 provisioning profile」是**不完整的**：group 名字带 TeamID 前缀确实免profile，但**签名本身必须有对应 TeamID**，否则授权不成立。

### 改动（project.pbxproj，4 个配置全改）
```
CODE_SIGN_STYLE = Automatic → Manual
DEVELOPMENT_TEAM = "" → MWYKGVPTJP
```

## 收菜记录支持「多次采收」（一条记录多个收菜时间）

### 需求澄清（重要：我第一次理解错了）
用户说「收菜记录编辑还可以增加时间」，我第一版理解成「顺带新增一条**别的菜**的记录」——**做错了**。
用户澄清：「是另外新增一条，是在**当前记录里**再增加一个收菜时间」。
→ 真实语义是**同一条记录有多个收菜时间**（分批采收），不是新增不同菜。
→ 做法：先 `git checkout --` 回退错误版本，再基于干净的 HEAD 重做。**方向搞错时及时回退，别在错方向上继续堆。**

### 数据结构（CropStore.swift）
```swift
struct CropRecord {
    ...
    var harvestAt: Date        // 由 let 改为 var（编辑时要能改）
    var extraHarvests: [Date] = []   // 追加的收菜时间
    var note: String?
}
```
派生属性：
- `allHarvests` = `([harvestAt] + extraHarvests).sorted()` —— **必须排序**，用户可任意顺序添加。
- `nextHarvest` = 第一个 > now 的时间点，全过期则 nil。倒计时/小组件都对准它。
- `isReady` = 任一时间点已到（展示高亮用）
- `isFullyHarvested` = 全部时间点已到（**清除已收获的判定标准**）

### 🔴 最重要的坑：加字段必须写自定义 init(from:)
Swift 合成的 `Decodable` 遇到**缺失字段直接抛 keyNotFound**，属性上的 `= []` 默认值
**只在成员初始化器里生效，管不到 Codable**。
后果：用户磁盘上所有旧 records.json 都没有 extraHarvests，升级后 `load()` 全部解码失败
→ `try?` 吞掉异常 → **静默返回空数组 = 记录全丢**。这是最坏的一类数据丢失。
```swift
init(from decoder: Decoder) throws {
    let c = try decoder.container(keyedBy: CodingKeys.self)
    ...
    extraHarvests = try c.decodeIfPresent([Date].self, forKey: .extraHarvests) ?? []  // 关键
    note = try c.decodeIfPresent(String.self, forKey: .note)
}
```
**连带坑**：一旦写了 `init(from:)`，合成的成员初始化器就**不再生成**，
CropStore 里两处 `CropRecord(...)` 构造点会报 `extra arguments`。必须再手写一个显式 init。
→ 顺序：先补显式 init，编译器才会告诉你哪里缺。

### 各处配套改动（漏一个就前后不一致）

## 续期模型重构：HarvestCycle 独立实体（每茬可单独编辑）

### 需求再次澄清（我第二版又只做了一半）
用户：「不是这样 我需要的当前记录里再新增一条收菜时间，**也可单独编辑**。因为这个菜会**反复种续期**」
→ 我上一版用 `extraHarvests: [Date]`，只能加/删，**不能单独改某一茬的时间**，也没有「已收」状态。
→ 正确模型：每茬是**独立实体**（有 id、有时间、有已收状态），列表里逐行可编辑。

### 数据结构：引入 HarvestCycle
```swift
struct HarvestCycle: Codable, Equatable, Identifiable {
    var id: String       // 稳定 id：ForEach/编辑/删除都按 id，不能用下标
    var date: Date
    var harvested: Bool  // 已收 vs 已过期未收，续期必须区分
}
struct CropRecord { ...; var harvests: [HarvestCycle] = []; var note: String? }
```
- `harvestAt` / `extraHarvests` 从存储字段降级为**仅解码用的迁移键**（仍留在 CodingKeys，encode 不写）。
- 派生：`nextHarvest`（未收且未到的最早）、`isReady`（有未收已到点的）、
  `isFullyHarvested`（全部已收或已过期）、`pendingCount`。

### 🔴 Codable 连锁反应（写自定义 init(from:) 的完整代价）
写了 `init(from:)` 之后，Swift **不再合成**另外两个，必须手动补齐，否则连续报错：
1. `encode(to:)` —— 报 `type does not conform to protocol 'Encodable'`（最隐蔽，不写就以为能编译）
2. 成员初始化器 —— 报 `extra arguments at positions #1..#7`
3. encode 时**只写新字段 harvests**，不写 harvestAt/extraHarvests，
   否则文件里存在两套时间，导入时语义歧义。
→ 规则：**给已有 struct 加字段且要兼容老数据 = 手写 init(from:) + encode(to:) + 显式 init，三件套。**

### 双代数据迁移路径（decode 里三分支）
```swift
if let v = try c.decodeIfPresent([HarvestCycle].self, forKey: .harvests) { harvests = v }
else {  // 第一代：只有 harvestAt；第二代：harvestAt + extraHarvests
    let first = try c.decode(Date.self, forKey: .harvestAt)
    let extras = try c.decodeIfPresent([Date].self, forKey: .extraHarvests) ?? []
    harvests = ([first] + extras).sorted().map { HarvestCycle(date: $0) }
}
```
用户磁盘上同时存在两代格式（第一代来自更早版本，第二代来自昨天那次改动），
**必须都覆盖**，否则老记录读不出来→ load() 静默返回空 → 记录全丢。

### UI：EditRecordSheet 整体重写
- 移除原来的「时间方式 Picker + 新增时长」单时间模型，改为**各茬列表** `cyclesSection`。
- `cycleRow(Binding<HarvestCycle>)`：勾选（已收）+ **独立 DatePicker** + 倒计时/「已收」+ 删除。
  每行完全独立编辑 —— 这正是上一版缺的。
- 「再续一茬」表单：`NewMode.afterLast`（基准=现有最晚一茬，连续续期不用重算）/ `.absoluteDate`。
- `addCycle()` 后自动 sort；`newDate` 同步为刚加的。
- `valid = !harvests.isEmpty`（至少留一茬）。
- 窗口包 ScrollView（茬数多了要滚），600×560。
- 列表行：显示 `nextHarvest`（无待收则显示最后一茬）+ `第N茬 · 已收M` 胶囊
  （hover 显示全部 `✓/○ + 时间`）。
- CropStore 新增 `renew(_:after:)`、`setHarvested(recordID:cycleID:_:)`。

## 倒计时实时刷新（TimelineView，按刷新粒度分层控性能）

### 问题
用户反馈「倒计时不是实时的」。根因：`remainText` 内部读 `Date()`，
但**没有任何东西驱动 body 重绘** —— SwiftUI 只在 @State 变化时重算，
所以倒计时停在 `58:19` 一动不动（截图对比前后完全相同）。

### 解法：按「变化频率」分层，各给各的粒度
| 元素 | 变化频率 | 方案 | 粒度 |
|---|---|---|---|
| 每行倒计时 | **秒级** | TimelineView 包**单个 Text** | 1s |
| 统计条 待收/可收获 | 跨到期时刻才变（分钟级） | TimelineView 包 3 个 tile | **5s** |
| 时刻文字 / 圆点 / 整张列表 | 数据变更时 | 不包，随 records 重建 | 无 |

### 🔴 性能关键决策（用户明确要求「考虑下性能再修改」）
1. **绝不能把 TimelineView 提到列表层**。
   `TimelineView(.periodic(by:1))` 包整个 ListView = 每秒重算并 diff 全部 N 条记录 × M 茬，
   50 条记录就是每秒几百次无效重建。
   现在只包住**倒计时那一个 Text**，外层圆点、时刻底色、卡片背景都不重绘。
2. **统计条用 5s 而非 1s**：「待收/可收获」只在某茬跨越到期时刻时突变，
   数字本身不逐秒变。5 秒粒度用户无感，开销降到 1/5。
3. **已收的茬直接 return 静态视图**（`.plain`/AnyView 分流），
   不创建 TimelineView —— 占了大多数的已收行完全零开销。
4. **用 TimelineView 而非自建 Timer**：
   - 调度由系统统一管理，多个行不会各起一个线程
   - App 切后台自动暂停，回到前台自动对齐（Timer 不会，容易累积漂移）
   - 无需手动 invalidate，避免泄漏
5. **同源时间**：新增 `remainText(_ target:now:)`，判定到期和算倒计时都用
   `context.date`，不混用 `Date()`。否则「是否过期」和「还剩多久」会差一次 tick，
   出现「显示可收但数字还是 00:01」的错位。

### 实现细节
- `harvestLine` 拆成两部分：静态部分（圆点 + 时刻底色）与 `countdownView(_:)`。
- `countdownView` 返回 `AnyView`，已收走静态分支、未收走 TimelineView 分支。
- 新增 `countReady(at:)` / `countPending(at:)` 接收传入时刻；
  原`readyCount` 保留（「清除已收获」按钮用），`pendingCount` 已无引用删除。
- 编辑弹窗每行倒计时同样包 TimelineView（行数少，开销可忽略），
  且顺带统一了样式：到期显示橙色「可收」胶囊，与主界面一致。

### 验证（截图实测，间隔 6 秒连拍）
第一张 `50:35 / 1:20:35 / 2:12:34 / 5:12:34` → 6 秒后
第二张 `50:28 / 1:20:28 / 2:12:27 / 5:12:27`
→ **四行全部 -7 秒，秒级刷新确认生效**（减少 7 秒是截图间隔 6s + 调度对齐所致，正常）。

## 收菜到点通知：修两个「一条都发不出来」的根本问题

### 用户需求
「时间到了发送通知」—— 原实现只有「提前 1 分钟」预告，到点本身没有通知。

### 🔴 根因1：沙盒缺personal-information 权限（致命）
entitlements 里只有 app-sandbox + application-groups + files.user-selected，
**缺 `com.apple.security.personal-information`**。
沙盒 App 没有这一项时，`UNUserNotificationCenter.add()` 会**静默失败**——
不抛异常、不打日志、一条通知都发不出来。表现就是「怎么配都不响」。
→ 已补 `com.apple.security.personal-information`。

### 🔴 根因2：没有 UNUserNotificationCenterDelegate（前台不弹横幅）
默认情况下 App 在**前台**时通知不显示横幅，只在后台/退出才显示。
用户看着 App 开着等待，永远等不到弹窗，误以为没发通知。
→ 改为 `final class CropNotifier: NSObject, UNUserNotificationCenterDelegate`，
  实现 `willPresent` 返回 `[.banner, .sound, .list]`。

**踩坑**：`enum CropNotifier: NSObject, ...` 编译不过 ——
报 `non-class type 'CropNotifier' cannot conform to class protocol`。
UNUserNotificationCenterDelegate 继承 NSObjectProtocol，**enum/struct 无法遵循，必须是 class**。
另外还要 `import os.log`（os_log 需要）。

### 其他改进
1. **每茬排两条**：`at-`（到点「可以收菜了」）+ `pre-`（提前1 分钟预告）。
   identifier 前缀区分类型 + 带时间戳，避免互相覆盖。
2. **授权异步**：原先 `requestPermission()` 后立刻 reschedule，
   授权未完成时 add() 会被丢弃。改为 `bootstrap()`：
   在 requestAuthorization 的**回调里**再 reschedule。
3. **回到前台重排**：`.onReceive(NSApplication.didBecomeActiveNotification)`
   —— 等待期间有些通知已触发/过期，不重排会留失效条目。
4. **interval 兜底**：`UNTimeIntervalNotificationTrigger` 要求 interval > 0，
   传 0 或负数会抛异常，`add()` 里 `guard secs > 0.5`。
5. **add() 带错误回调**：把 os_log 打出来，不再静默吞错。

### 🔴 逻辑 bug（测试发现的）：已收的茬还在排通知

## 倒计时临近高亮（≤20 分钟三级递进）

### 需求
「倒计时小于20分钟需要高亮一点」。

### 三档递进（不只是改数字颜色，视野层级也递进）
| 状态 | 倒计时 | 时刻块| 卡片左边条 |
|---|---|---|---|
| > 20 分钟 | 灰色 callout 半粗 | 蓝底 16% | 无 |
| **≤ 20 分钟** | **白字 + 橙底 + bold** | **橙底 22%** | **橙条 3pt** |
| 已到期 | 「可收」橙胶囊 | 橙底 22% | 橙条 3pt |

**为什么加卡片左边条**：行内高亮只占卡片一小块位置，列表一长扫视时容易漏。
加一条贯穿整卡高度的 3pt 竖边，让「快到点 / 已到点」的记录在余光里也能捕捉到。
`cardHighlightTint` 计算属性：任一未收茬 `timeIntervalSinceNow <= urgentSeconds` 就返回 .orange。

### 实现要点
- 阈值提为 `private static let urgentSeconds: TimeInterval = 20 * 60`，一处定义三处引用
  （harvestLine 的时刻配色、countdownView 的倒计时、cardHighlightTint 的竖条）。
- **时刻块仍不包 TimelineView**：它用 `Date()` 粗算临近态即可（分钟级精度够用），
  秒级变化交给右边本来就在每秒重建的倒计时。这样高亮不增加任何重绘开销。
- 判定用 `left <= 0 || left <= urgentSeconds`，把「已到期」并入橙色分支，
  避免两种橙色并存。

### 🔴 又踩了一次括号错误（第三次，已成习惯性 bug）
在 `RecordRow.body` 末尾追加 `.overlay` 后，多加了一个 `}` 把struct 提前关掉，
`harvestLine` / `countdownView` / `urgentSeconds` 全部掉到文件作用域，
报 `Static properties may only be declared on a type` / `Expected '}' in struct`，
错误行号飘到 900+ 行，跟真实原因（822 行）毫无关系。

**根治办法（以后每次改完大结构就跑一遍）**：
写个几行的括号深度校验脚本，逐行累计 `{`/`}`（先 `split('//')[0]` 去掉注释），
输出每个 `struct/class/enum` 的「前置深度」+ 文件末尾深度。
前置深度全为 0、末尾深度为 0 就说明结构没崩。比读编译错误快得多，
也不依赖编译器把位置报在远处。这个脚本对本项目这种 1300+ 行的单文件尤其有用。

## 续期新增第三个 tab：「从当前起算」

### 需求
「新增时间再增加一个 tab，在当前时间上增加时间」

### 为什么这个 tab 有实际价值（测试证实的关键点）
原来只有 afterLast（以上一茬为基准）和 absoluteDate（指定绝对时间）。
**续期场景的典型问题**：上一茬是 3 天前收的，现在想重新种一棵，填 2 小时：
- afterLast → 09-19 00:13  **已经过去的时间**（3天前 + 2小时）→ 加进去立刻显示「可收」，没意义
- fromNow   → 09-22 00:13  ✓ 正确的未来时间
两者差 72 小时。afterLast 在「上一茬已过期」的记录上算出来必然是过去时间。

### 改动（EditRecordSheet）
```swift
enum NewMode: String, CaseIterable, Identifiable {
    case afterLast = "在上一茬之后"
    case fromNow = "从当前起算"      // 新增
    case absoluteDate = "按指定时间"  // 原「按指定收菜时间」缩短，避免 segmented 控件过宽
    /// 是否需要填「小时 + 分钟」
    var usesDuration: Bool { self != .absoluteDate }
}
```
- `previewNewDate` 改成 switch 三分支；`fromNow` 用 `Date()`（不是 `record.plantedAt`）。
- `usesDuration` 抽出来，UI 判断从 `newMode == .afterLast` 改为 `newMode.usesDuration`，
  加第三个 tab 时不用改 UI 分支。
- **`newModeHint`**：每个 tab 下方小字说明基准（「以上一茬 MM-dd HH:mm 为基准」/
  「从现在（MM-dd HH:mm）起算」）。两个"填间隔"的 tab 基准不同，不写清楚
  用户会以为「在上一茬之后」=「现在」。
- **`canAddCycle`**：填 0 分钟 / 选出过去的时间时**禁用「添加」**，
  避免往列表塞一个立即显示「可收」的无效茬。
- Picker `frame(maxWidth: 320 → 420)`，容纳三个 tab。

### 主界面没改
主界面「成熟时长」是**新建记录**，从当下起算本就是默认行为，无需加这个 tab。

### 验证
swiftc 独立跑三模式计算：afterLast 算出过去时间（确认问题真实存在）、
fromNow 算出未来时间（正确）、absoluteDate 直接用指定值；
usesDuration 分流正确（两个 true 一个 false）。
括号深度校验通过。
